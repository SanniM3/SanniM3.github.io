Why Attention Is Expensive

Why Attention Is Expensive: The Compute and Memory Costs Hidden in a Single Equation

25 min read

The Transformer owes much of its success to a seemingly simple architectural decision: replace recurrence with self-attention. Instead of forcing information to travel through a sequence one step at a time, attention allows distant positions to interact directly. In a bidirectional Transformer, a token can attend to every other token in the sequence; in the causal Transformers used by most large language models, it can attend to every token that came before it. This made long-range information easier to access while also removing the inherently sequential computation of recurrent networks, allowing far more of the training workload to be parallelised. This combination was central to the success of the original Transformer architecture introduced in Attention Is All You Need.

But the same global interaction that makes self-attention powerful also gives it an 'expensive' scaling property. Every additional token does not simply add another unit of work. It creates new interactions with all of the tokens already in the sequence. As context windows grow from hundreds of tokens to thousands or tens of thousands, those interactions accumulate quickly.

This is the reason for the familiar statement that attention is quadratic in sequence length. Double the context length and there are roughly four times as many token-to-token interactions. Increase it from 2,048 tokens to 16,384 and the number of interactions grows by a factor of sixty-four.

Yet saying that attention is \(O(n^2)\) only tells part of the story.

The other part is how the attention computation interacts with modern hardware. A straightforward implementation creates an \(n\times n\) matrix of attention scores, applies a softmax to it, and then uses the result to aggregate the value vectors. Those intermediate tensors can become enormous, and moving them through GPU memory can cost enough that data movement, rather than arithmetic, becomes a major performance bottleneck. This distinction between computation and memory traffic is the central insight behind algorithms such as FlashAttention.

So to understand why attention became expensive, we need to look at it from two perspectives. First, there is the algorithm itself: where exactly does the quadratic amount of work come from? Second, its implementation: why can two implementations of exactly the same attention equation have dramatically different runtimes and memory requirements?

That is what this article is about.

The attention equation hides a lot of work

Scaled dot-product attention is given as:

$$ \operatorname{Attention}(Q,K,V) = \operatorname{softmax} \left( \frac{QK^\top}{\sqrt{d_h}} \right)V. $$

The compactness of the notation makes the operation look almost trivial. But the expensive part is hidden inside \(QK^\top\).

Suppose we have a sequence containing \(n\) tokens. For one attention head, each token is represented by a query, key and value vector of dimension \(d_h\):

$$ Q,K,V \in \mathbb{R}^{n\times d_h}. $$

Consider a single query vector \(q_i\). To decide how much information token \(i\) should gather from the sequence, we compare this query with every key:

$$ q_i^\top k_1,; q_i^\top k_2,; \dots,; q_i^\top k_n. $$

There are \(n\) comparisons for this one query. But since there are also \(n\) queries in the sequence, the models therefore computes \(n\times n=n^2\) query-key similarities. Written as a matrix operation,

$$ QK^\top \in \mathbb{R}^{n\times n}. $$

That \(n\times n\) object is the attention-score matrix. Entry \((i,j)\) measures the compatibility between the query produced by token \(i\) and the key produced by token \(j\).

For causal attention, the future portion of this matrix is masked because token \(i\) is not allowed to see tokens \(j>i\). The number of valid interactions is therefore roughly \(n(n+1)/2\) rather than \(n^2\). That changes a constant factor, not the asymptotic behaviour: the number of interactions still grows quadratically.

This is the first source of expense.

"Attention performs global pairwise interaction, and global pairwise interaction naturally produces a quadratic number of pairs."

From \(n^2\) comparisons to actual computation

Saying that there are \(n^2\) attention scores is not quite enough to describe the computational cost, because calculating each score itself requires work.

Each query and key contains \(d_h\) elements. Calculating one dot product therefore takes \(O(d_h)\) operations. Across the entire score matrix, a single attention head requires

$$ O(n^2d_h) $$

work.

With \(h\) heads, the cost becomes

$$ O(hn^2d_h). $$

Because the model dimension is normally

$$ d_{\text{model}} = h d_h, $$

we can write this more simply as

$$ O(n^2d_{\text{model}}). $$

And that is only the first matrix multiplication.

After the softmax produces the attention probabilities \(P\),

$$ P = \operatorname{softmax} \left( \frac{QK^\top}{\sqrt{d_h}} \right), $$

we still need to compute

$$ PV. $$

Here \(P\) has shape \(n\times n\) and \(V\) has shape \(n\times d_h\), so this multiplication also costs

$$ O(n^2d_h) $$

per head.

If we count a multiplication and an addition as two floating-point operations, then the two large attention matrix multiplications together require approximately

$$ 4n^2d_{\text{model}} $$

FLOPs for a batch size of one.

This gives us a more concrete way to reason about attention than simply saying "\(O(n^2)\)."

Take a Transformer with

$$ d_{\text{model}}=4096, $$

implemented as 32 attention heads with a head dimension of 128. At a context length of 4,096 tokens, the two attention matrix multiplications require approximately

$$ 4(4096)^2(4096) \approx 2.75\times10^{11} $$

floating-point operations.

That is around 275 billion FLOPs, or 0.275 TFLOPs, for the attention matrix multiplications in one layer and one sequence.

Note the distinction between FLOPs and FLOP/s. A TFLOP is \(10^{12}\) floating-point operations; however, a GPU rated in TFLOP/s describes how many of those operations it can theoretically perform per second.

Quadratic does not mean attention always dominates the FLOP count

There is an important qualification here.

It is tempting to jump from

attention scales as \(n^2\)

to

attention is ALWAYS the most computationally expensive part of a Transformer.

That is not necessarily true.

The query, key, value and output projections are dense linear layers. Their computational cost scales approximately as

$$ O(nd_{\text{model}}^2), $$

which is linear in sequence length but quadratic in model width.

The feed-forward network behaves similarly with respect to sequence length. It performs substantial computation independently for every token, so its cost also grows linearly with \(n\).

This means that for short and moderate context lengths, the MLP and projection layers can consume more FLOPs than attention. The fact that attention is quadratic does not automatically make it the dominant operation at every sequence length.

For our \(d_{\text{model}}=4096\) example, the \(Q\), \(K\), \(V\) and output projections together require approximately

$$ 8nd_{\text{model}}^2 $$

FLOPs.

At \(n=4096\), that is about 0.55 TFLOPs, roughly twice the arithmetic required by the \(QK^\top\) and \(PV\) matrix multiplications.

This observation is useful because it clarifies what makes attention 'expensive'. The problem is not that attention is always the largest computation in a Transformer. The problem is that attention is the component whose cost grows quadratically as we increase context length. For fixed model width,

$$ \text{projection and MLP cost} \propto n, $$

whereas

$$ \text{full-attention cost} \propto n^2. $$

Eventually, as \(n\) becomes large enough, that difference dominates.

The second quadratic object: memory

So far we have only counted arithmetic. Now consider what a straightforward implementation actually stores. For each head,

$$ QK^\top $$

produces an \(n\times n\) score matrix.

With \(h\) heads and batch size \(B\), the score tensor has shape

$$ B\times h\times n\times n. $$

If each element takes \(s\) bytes, then storing that tensor requires \(Bhn^2s\) bytes.

The quadratic dependence appears again!

Suppose we use 32 heads, a batch size of one and FP16 or BF16 values, which require two bytes per element. The raw score tensor alone would have the following approximate sizes:

Context length Score matrix, one head Score tensor, 32 heads
512 0.5 MiB 16 MiB
2,048 8 MiB 256 MiB
4,096 32 MiB 1 GiB
8,192 128 MiB 4 GiB
32,768 2 GiB 64 GiB

These figures refer only to the dense attention-score tensor for a single layer. They do not include \(Q\), \(K\), \(V\), the output, model weights, MLP activations, gradients or optimiser state.

And importantly, the mathematical definition of attention does not require us to keep this entire matrix resident in memory. The quadratic intermediate-memory cost arises from a conventional implementation that materialises the score or probability matrix. Algorithms such as FlashAttention demonstrate that exact full attention can be reorganised so that this full \(n\times n\) intermediate is never stored in high-bandwidth memory.

That distinction is important:

full attention has quadratic arithmetic complexity, but quadratic auxiliary memory is not inevitable.

It is an implementation property that can be changed.

Why FLOPs do not tell the whole story

At this point, it might seem that we have already answered the question.

Attention is expensive because it performs \(O(n^2d)\) arithmetic and, in a straightforward implementation, creates \(O(n^2)\) intermediate tensors.

But this still does not explain why optimising attention has required so much systems work.

To understand that, we need to stop thinking of a GPU as a single machine that "does FLOPs."

A modern GPU contains a hierarchy of compute and memory resources. NVIDIA's CUDA programming model describes each GPU as a collection of streaming multiprocessors, or SMs. Each SM contains compute units alongside a local register file, L1 cache and shared memory. Outside the SMs sits much larger device memory, typically implemented using high-bandwidth memory on data-centre accelerators. Registers and shared memory are small but extremely fast; global device memory is far larger, but accessing it is comparatively more expensive.

This difference creates an important distinction between doing arithmetic and moving the data needed for that arithmetic.

Modern GPUs have been designed to perform dense matrix multiplication exceptionally efficiently. Once appropriately sized matrix tiles are available to the compute units, enormous numbers of multiply-accumulate operations can be performed in parallel.

But those values first have to get there.

And after intermediate results are produced, those results have to go somewhere.

For some algorithms, the ratio of arithmetic to data movement is high. The GPU loads a piece of data and performs a large amount of useful computation with it before writing a result back.

For other algorithms, significant amounts of data are read and written relative to the amount of arithmetic performed. These workloads are much more sensitive to memory bandwidth.

Attention contains both behaviours.

The large \(QK^\top\) and \(PV\) matrix multiplications map well onto GPU matrix-multiplication hardware. But a conventional attention implementation surrounds those multiplications with operations that create, transform, store and reload an enormous \(n\times n\) intermediate.

That is where things become interesting.

What a straightforward implementation actually does

Consider the attention equation again:

$$ O = \operatorname{softmax} \left( \frac{QK^\top}{\sqrt{d_h}} \right)V. $$

Mathematically this is one expression.

A straightforward GPU implementation, however, can decompose it into several stages.

First, \(Q\) and \(K\) are read and multiplied to produce the score matrix

$$ S = QK^\top. $$

Because \(S\) may be too large to remain entirely in the small amount of fast memory available on an SM, it is written to global GPU memory.

The softmax kernel then needs \(S\), so the scores are read again. The kernel calculates row-wise maxima and normalisation terms, applies exponentiation and produces the probability matrix

$$ P = \operatorname{softmax}(S). $$

That result may then be written back to global memory.

Finally, another matrix multiplication needs \(P\) and \(V\), so the attention probabilities are read again before computing

$$ O=PV. $$

The exact sequence of reads, writes and fused operations depends on the framework and kernel implementation. Modern libraries can fuse some of these stages, so this should not be interpreted as a description of every attention kernel in use today. But it captures the problem that motivated IO-aware attention algorithms: materialising the large intermediate attention matrix creates substantial traffic between global memory and the GPU's on-chip storage. FlashAttention was explicitly designed around reducing these HBM reads and writes.

On-chip registers and shared memory are much closer to the compute units and can be accessed much more quickly, but their capacity is tiny compared with device memory. The performance challenge is therefore to structure computations so that data loaded into fast memory is reused as much as possible before being evicted. NVIDIA's own CUDA documentation describes shared memory as a software-managed scratchpad that can be used specifically to minimise accesses to global memory.

Attention, implemented naïvely, does a poor job of exploiting that hierarchy because the \(n\times n\) intermediate grows far beyond what on-chip storage can hold.

Compute complexity and IO complexity are different questions

This gives us two different ways of asking how expensive attention is.

The first is:

How many mathematical operations are required?

For exact dense attention, the answer grows quadratically with sequence length:

$$ O(n^2d). $$

The second is:

How much data must move between different levels of memory while those operations are being performed?

That is an IO-complexity question.

These are related, but they are not the same.

Two algorithms can compute mathematically equivalent results using roughly the same number of arithmetic operations while generating very different amounts of memory traffic.

FlashAttention is the clearest example. It does not replace full attention with a sparse or approximate alternative. Instead, it reorganises the exact attention computation around the GPU memory hierarchy. It divides \(Q\), \(K\) and \(V\) into tiles that can fit in on-chip memory and computes attention incrementally, using an online form of softmax so that the entire score matrix never needs to be written to HBM. The result is the same attention function, up to the normal differences introduced by floating-point evaluation order, but with far less intermediate-memory traffic.

That result is conceptually important because it shows that there are really two problems hiding inside "attention is expensive."

One problem comes from the algorithm: all-to-all interaction creates quadratic computation.

The other comes from the implementation: materialising all of those interactions creates unnecessary memory traffic.

FlashAttention can dramatically improve the second problem.

It does not make the first one disappear.

Why long context changes everything

The easiest way to see why this matters is to look at how the two costs scale.

If we double \(n\),

$$ n\rightarrow2n, $$

then the number of attention scores becomes

$$ (2n)^2=4n^2. $$

Double the context again and the original workload has increased sixteen-fold.

This scaling is why context length is such an important systems parameter for LLMs. Moving from a 2K context window to an 8K context window does not merely process four times as many tokens inside attention. It creates sixteen times as many potential pairwise interactions during a full attention pass.

At 32K tokens, a single attention head contains more than one billion score positions:

$$ 32768^2 = 1{,}073{,}741{,}824. $$

At two bytes per value, explicitly storing that matrix requires 2 GiB for one head.

With 32 heads, a fully materialised dense score tensor would require approximately 64 GiB for a single layer and a batch size of one.

Of course, modern attention implementations do not need to materialise such a tensor. That is precisely why memory-efficient kernels are so important. But the numbers reveal the pressure that caused those kernels to become necessary.

Training, prefill and decoding are not the same workload

There is one final distinction worth making before we leave the problem itself and start discussing solutions.

When we describe attention as quadratic, we are primarily describing a full-sequence attention computation. That is what happens during training, where many token positions are processed together, and during the prefill stage of LLM inference, where an input prompt is processed (and the initial key-value casche is built) before generation begins.

Autoregressive decoding behaves differently.

Once a model has processed the existing context, it generates one new token at a time. The query for that new token only needs to attend over the keys and values belonging to previous tokens. If those keys and values are cached, the attention calculation for a single new token grows linearly with the current context length rather than quadratically.

But avoiding recomputation creates a different systems problem: the keys and values for every previous token must now be stored and repeatedly accessed.

That is the KV-cache problem, and it leads directly to Multi-Query Attention, Grouped-Query Attention and memory-management techniques such as PagedAttention. Multi-Query Attention was explicitly motivated by the memory-bandwidth cost of repeatedly loading key and value tensors during incremental decoding, while Grouped-Query Attention later introduced a compromise between standard multi-head attention and fully shared key/value heads.

That is a different bottleneck from the one we have studied here, and it deserves its own treatment.

It will be the subject of the next article.

So why is attention expensive?

We can now answer the question more precisely than simply saying "because it is \(O(n^2)\)."

Full self-attention is expensive because global token interaction produces a quadratic number of query-key relationships. Computing those relationships and using them to aggregate the value vectors requires \(O(n^2d)\) arithmetic. Unlike the projections and feed-forward layers of a Transformer, whose cost grows linearly with sequence length for fixed model width, attention becomes increasingly expensive as the context window grows.

But arithmetic complexity is only half of the picture.

A conventional implementation also materialises an \(n\times n\) intermediate attention matrix. At long context lengths, this tensor becomes enormous. Writing it to GPU memory, reading it for softmax, writing the resulting probabilities and reading them again for the value aggregation creates substantial data movement through the GPU memory hierarchy.

The first problem is algorithmic.

The second is architectural and implementation-dependent.

And that distinction explains much of the evolution of modern attention systems.

Techniques such as FlashAttention ask:

How can we compute the same full attention operation while moving much less data?

Techniques used for efficient decoding ask:

How can we avoid recomputing past information, and how can we reduce the amount of cached state that must be moved for every generated token?

Those questions lead in different directions.

In Article 2, we will follow the inference path: why autoregressive decoding led to the KV cache, why the cache itself became a memory-bandwidth bottleneck, and how Multi-Query and Grouped-Query Attention reduce it.

In Article 3, we will return to the full attention computation and follow the hardware path: how FlashAttention uses tiling and online softmax to avoid materialising the attention matrix, why IO-awareness matters, and how the algorithm evolved through FlashAttention-2 and FlashAttention-3.

The attention equation itself will remain almost unchanged throughout. What changes is how we choose to execute it.
