Implementing LoRA from Scratch

30 min read

Fine-tuning large language models is expensive. A 7B-parameter model needs around 28 GB just to store its weights in float32, and training requires additional memory for gradients, optimiser states, and activations. With a conventional Adam-based training setup, full fine-tuning can easily push the memory requirement beyond 100 GB.

This is where LoRA comes in.

LoRA, or Low-Rank Adaptation, starts from a simple idea: when we fine-tune a pretrained model, perhaps we do not need to give every weight in the model complete freedom to move independently. Instead, LoRA constrains the weight update to a much smaller, low-rank representation.

The result is that the original model stays frozen, while we train a relatively tiny collection of additional parameters. We still adapt the model to a new task, but we avoid storing gradients and optimiser states for billions of pretrained parameters.

In this post, I will build LoRA from scratch. Rather than jumping straight from the equation \(\Delta W = BA\) into code, we'll derive where that equation comes from, look carefully at the dimensions of the matrices involved, see exactly how the maths maps onto PyTorch, and then build the machinery needed to inject LoRA into an existing model and train it.

The problem with full fine-tuning

Consider a linear layer in a pretrained neural network:

$$h = W_0 x$$

where

$$W_0 \in \mathbb{R}^{d_{\text{out}} \times d_{\text{in}}}$$

is the pretrained weight matrix.

During full fine-tuning, we allow every element of \(W_0\) to change. After training, we can think of the new weight matrix as

$$W = W_0 + \Delta W$$

where \(\Delta W\) represents everything fine-tuning has changed about that layer.

The forward pass can therefore be written as

$$h = (W_0 + \Delta W)x$$

or, equivalently,

$$h = W_0x + \Delta Wx$$

This second form is the useful one.

It tells us that adapting the model does not necessarily require us to overwrite \(W_0\). We could keep the pretrained transformation \(W_0x\) exactly as it is and learn a second transformation, \(\Delta Wx\), that represents the adaptation.

The problem is that if \(\Delta W\) is unrestricted, it is just as large as \(W_0\). For a weight matrix with shape \(d_{\text{out}} \times d_{\text{in}}\), it contains

$$d_{\text{out}}d_{\text{in}}$$

trainable values.

And training those values costs more memory than simply storing them.

Why training uses so much memory

Suppose we train with Adam. For each trainable parameter we typically need to keep track of:

  • The parameter itself
  • Its gradient
  • Adam's first-moment estimate (often described as momentum)
  • Adam's second-moment estimate (the squared-gradient or variance-like estimate)

If all four are stored in float32, each value occupies 32 bits. Since 8 bits make one byte:

$$32 / 8 = 4 \text{ bytes}$$

A 7B-parameter model therefore requires approximately

$$7 \times 10^9 \times 4 = 28 \times 10^9 \text{ bytes} \approx 28\text{ GB}$$

just for the parameters.

If we use the simple float32 Adam accounting above, the parameter, gradient, and two optimiser states give us four float32 values per trainable parameter:

$$28\text{ GB} \times 4 = 112\text{ GB}$$

and that is before accounting for activations, temporary buffers, and other training overhead.

Mixed-precision training changes the exact accounting, and modern training systems can shard or offload some of these tensors, so there is no single universal memory number. But the central problem remains: making billions of parameters trainable means storing training state for billions of parameters.

LoRA attacks that problem directly.

From a full update to a low-rank update

LoRA is motivated by the hypothesis that the changes required to adapt a large pretrained model have much lower intrinsic dimensionality than the full parameter space available to the model.

Instead of learning an unrestricted matrix \(\Delta W\), LoRA parameterises it as the product of two much smaller matrices:

$$\Delta W = BA$$

with

$$A \in \mathbb{R}^{r \times d_{\text{in}}}$$

and

$$B \in \mathbb{R}^{d_{\text{out}} \times r}$$

where

$$r \ll \min(d_{\text{in}}, d_{\text{out}}).$$

Multiplying the two matrices gives

$$ \underbrace{B}_{d_{\text{out}}\times r} \underbrace{A}_{r\times d_{\text{in}}} = \underbrace{\Delta W}_{d_{\text{out}}\times d_{\text{in}}}. $$

So \(BA\) has exactly the shape we need. It can be added to \(W_0\), but we only have to train the elements of \(A\) and \(B\).

What does "low-rank" actually mean?

The rank of a matrix is, loosely speaking, the number of independent directions that matrix can represent.

The important property here is

$$\operatorname{rank}(BA) \leq r.$$

If \(r = 8\), for example, then no matter how large \(W_0\) is, the update produced by \(BA\) has rank at most 8.

Another useful way to think about this is as a bottleneck:

$$d_{\text{in}} \rightarrow r \rightarrow d_{\text{out}}.$$

The input is first projected from its original dimension into a small \(r\)-dimensional space by \(A\), and then projected back to the output dimension by \(B\).

For \(r=8\), the adaptation is therefore forced to operate through only eight intermediate dimensions.

This is the constraint LoRA imposes. Rather than allowing fine-tuning to choose any possible \(\Delta W\), we only allow updates that can be expressed through this small bottleneck.

A quick note on matrix decomposition

If you've seen singular value decomposition (SVD), the idea of representing a large matrix using a smaller number of directions may feel familiar. A low-rank approximation can often capture much of a matrix's structure with far fewer values.

But it is worth being precise here: LoRA does not first train a full \(\Delta W\) and then run SVD on it.

We never construct an unrestricted update in the first place.

Instead, we define

$$\Delta W \equiv BA$$

from the beginning and optimise \(A\) and \(B\) directly.

Why this saves so many parameters

A full update matrix requires

$$d_{\text{out}}d_{\text{in}}$$

parameters.

LoRA instead requires

$$rd_{\text{in}} + d_{\text{out}}r$$

which can be written as

$$r(d_{\text{in}} + d_{\text{out}}).$$

Consider a square \(4096 \times 4096\) attention projection.

The original matrix contains

$$4096^2 = 16,777,216$$

parameters.

At rank \(r=8\), LoRA requires

$$8(4096 + 4096) = 65,536$$

trainable parameters:

  • \(A\): \(8 \times 4096 = 32,768\)
  • \(B\): \(4096 \times 8 = 32,768\)

The fraction of parameters being trained is therefore

$$\frac{65,536}{16,777,216} \approx 0.0039.$$

That's about 0.39% as many trainable parameters, or a 256× reduction for that matrix.

This does not make the original matrix disappear. We still need \(W_0\) for the forward pass. What disappears is the need to maintain gradients and optimiser states for every element of \(W_0\).

The complete LoRA forward pass

So far we have

$$h = W_0x + BAx.$$

The actual LoRA formulation introduces one more factor:

$$h = W_0x + \frac{\alpha}{r}BAx.$$

There are now two important hyperparameters:

  • \(r\) controls the rank, and therefore the capacity and parameter count of the adapter.
  • \(\alpha\) controls the scale of the LoRA update relative to the frozen pretrained path.

The quantity that actually multiplies the adapter output is

$$\frac{\alpha}{r}.$$

Why divide by the rank?

Changing \(r\) changes more than just the number of parameters. It also changes the number of latent components contributing to the update.

The \(\alpha/r\) factor gives us an explicit way to control the scale of the adaptation as we change rank. For example, if

$$r=8,\qquad \alpha=16,$$

then

$$\frac{\alpha}{r}=2.$$

If we later use \(r=16\) and \(\alpha=32\), the adapter has more capacity but the explicit scaling factor remains 2.

This does not mean that \(\alpha\) must always equal \(2r\), or that there is a universal best value. Rank and scaling are hyperparameters to validate for the task. The important point is that they control different things: rank controls representational capacity; \(\alpha\) controls the contribution of that representation to the layer output.

How the equation becomes PyTorch

Before writing a class, let's translate the mathematics into the convention PyTorch uses.

Mathematically, we often write an individual input as a column vector and express the LoRA path as

$$BAx.$$

PyTorch usually stores batches of activations with the feature dimension on the right. If

$$x \in \mathbb{R}^{b \times d_{\text{in}}},$$

then the first multiplication is

$$ \underbrace{x}_{b\times d_{\text{in}}} \underbrace{A^T}_{d_{\text{in}}\times r} = \underbrace{xA^T}_{b\times r}. $$

This is the bottleneck. We have reduced the feature dimension from \(d_{\text{in}}\) to \(r\).

Then:

$$ \underbrace{xA^T}_{b\times r} \underbrace{B^T}_{r\times d_{\text{out}}} = \underbrace{xA^TB^T}_{b\times d_{\text{out}}}. $$

Because

$$(BA)^T = A^TB^T,$$

this is the row-vector/batched PyTorch equivalent of applying \(BA\) to the input.

In code, the entire adapter path is therefore just:

adapter = x @ self.lora_A.T
adapter = adapter @ self.lora_B.T

Or, using PyTorch's linear operation:

adapter = F.linear(x, self.lora_A)
adapter = F.linear(adapter, self.lora_B)

I prefer the second version in the implementation because each line directly represents one linear projection.

Why not calculate \(BA\) first?

You might reasonably ask why we don't simply construct the update matrix:

delta_w = self.lora_B @ self.lora_A
adapter = F.linear(x, delta_w)

Mathematically, that works.

But it throws away one of the useful properties of the low-rank representation. The matrix

$$BA \in \mathbb{R}^{d_{\text{out}}\times d_{\text{in}}}$$

is large again. Instead, we can exploit associativity and evaluate the two small transformations sequentially:

$$d_{\text{in}} \rightarrow r \rightarrow d_{\text{out}}.$$

During training, there is no reason to materialise the full update matrix.

We will only explicitly calculate \(BA\) later, when we want to merge the learned adapter into the pretrained weight for inference.

Implementation: building the LoRA layer

Now the implementation should look much less mysterious.

Instead of creating a brand-new linear layer and copying the pretrained weights into it, I'll make our LoRA layer wrap an existing nn.Linear. This preserves its weight, bias, device and dtype.

We start with the constructor:

import torch
import torch.nn as nn
import torch.nn.functional as F


class LoRALinear(nn.Module):
    def __init__(
        self,
        base_layer: nn.Linear,
        r: int = 8,
        alpha: float = 16.0,
        dropout: float = 0.0,
    ):
        super().__init__()

        if r <= 0:
            raise ValueError("LoRA rank must be positive")

        self.in_features = base_layer.in_features
        self.out_features = base_layer.out_features
        self.r = r
        self.alpha = alpha
        self.scaling = alpha / r
        self.merged = False

The important line here is:

self.scaling = alpha / r

which corresponds directly to the scaling term in

$$W_0x + \frac{\alpha}{r}BAx.$$

Keeping the pretrained weights frozen

Next, we reuse the existing linear layer's parameters:

        self.weight = base_layer.weight
        self.bias = base_layer.bias

        self.weight.requires_grad_(False)

        if self.bias is not None:
            self.bias.requires_grad_(False)

There is no copy of \(W_0\) here. self.weight refers to the original pretrained parameter.

The important change is:

self.weight.requires_grad_(False)

Autograd can still use this matrix to compute the forward pass and propagate gradients through the network, but PyTorch will not accumulate a gradient for the weight itself.

That distinction is central to LoRA: the pretrained model participates in the computation, but its parameters are not being optimised.

Creating \(A\) and \(B\)

Now we create the trainable matrices:

        factory_kwargs = {
            "device": self.weight.device,
            "dtype": self.weight.dtype,
        }

        self.lora_A = nn.Parameter(
            torch.empty(r, self.in_features, **factory_kwargs)
        )

        self.lora_B = nn.Parameter(
            torch.empty(self.out_features, r, **factory_kwargs)
        )

        self.dropout = (
            nn.Dropout(dropout)
            if dropout > 0.0
            else nn.Identity()
        )

The shapes correspond exactly to our equations:

$$A \in \mathbb{R}^{r\times d_{\text{in}}}$$
$$B \in \mathbb{R}^{d_{\text{out}}\times r}.$$

Notice that the new tensors are constructed using the device and dtype of the pretrained weight. That matters when injecting the layer into a model that is already on a GPU or stored in something like bfloat16.

Why LoRA uses asymmetric initialisation

We now initialise \(A\) randomly and \(B\) to zero:

        self.reset_parameters()


    def reset_parameters(self):
        nn.init.kaiming_uniform_(self.lora_A, a=5**0.5)
        nn.init.zeros_(self.lora_B)

The exact random initialisation used for \(A\) can vary between implementations. The property we really care about is that \(B\) starts at zero.

At initialisation:

$$B=0.$$

Therefore:

$$BA = 0,$$

and the layer computes

$$ h = W_0x + \frac{\alpha}{r}(0)x = W_0x. $$

So immediately after inserting LoRA, the model behaves like the original pretrained model.

This is a very nice property. We have added new trainable parameters without initially perturbing the function the pretrained model has already learned.

But if \(B=0\), can training even start?

Yes.

This is a subtle detail that is easy to miss.

Let the LoRA contribution be

$$z = BAx.$$

The gradient with respect to \(B\) depends on the output of \(A\). Since \(A\) was initialised randomly, \(Ax\) is generally non-zero. That means \(B\) can receive a useful gradient on the very first backward pass.

The gradient with respect to \(A\), however, contains \(B\). Since \(B=0\) initially, the first gradient for \(A\) is zero.

After the first optimiser step, \(B\) is no longer zero. From then on, both matrices can learn.

So the initialisation gives us two useful properties at once:

  • The adapter initially changes nothing.
  • Training can still begin immediately through \(B\).

Writing the forward pass

Now we can implement the equation one piece at a time.

First, the frozen pretrained path:

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        if self.merged:
            return F.linear(x, self.weight, self.bias)

        base_output = F.linear(x, self.weight, self.bias)

This is simply

$$W_0x.$$

Then the low-rank path:

        adapter_input = self.dropout(x)

        adapter_output = F.linear(
            adapter_input,
            self.lora_A,
        )

        adapter_output = F.linear(
            adapter_output,
            self.lora_B,
        )

The first call performs

$$xA^T,$$

taking us from \(d_{\text{in}}\) dimensions down to \(r\).

The second performs

$$xA^TB^T,$$

taking us from \(r\) back to \(d_{\text{out}}\).

Finally, we scale the adapter and add it to the base output:

        return base_output + adapter_output * self.scaling

Putting the pieces together, the code is implementing

$$h = W_0x + \frac{\alpha}{r}BAx.$$

That is essentially LoRA.

Everything else we need is machinery around this equation: inserting the adapters into a model, choosing which layers to adapt, training only \(A\) and \(B\), saving them, and optionally merging them into the original weights.

Merging the adapter for inference

During training we deliberately keep the two paths separate:

$$W_0x + \frac{\alpha}{r}BAx.$$

After training, however, \(A\) and \(B\) are fixed. We can therefore calculate

$$W_{\text{merged}} = W_0 + \frac{\alpha}{r}BA$$

once and use the resulting matrix as an ordinary linear layer.

Let's add that to our class:

    @torch.no_grad()
    def merge(self):
        if self.merged:
            return

        delta_w = self.lora_B @ self.lora_A
        self.weight.add_(delta_w * self.scaling)
        self.merged = True


    @torch.no_grad()
    def unmerge(self):
        if not self.merged:
            return

        delta_w = self.lora_B @ self.lora_A
        self.weight.sub_(delta_w * self.scaling)
        self.merged = False

I use torch.no_grad() here because merging is not part of optimisation. We are deliberately modifying the stored pretrained parameter for deployment.

Once merged, the forward pass is simply:

F.linear(x, self.weight, self.bias)

so LoRA does not require an additional inference branch.

For a minimal implementation, reversible merging is convenient. In a production system, I would be careful about repeatedly merging and unmerging low-precision weights because repeated addition and subtraction can introduce small numerical errors.

The complete LoRA layer

Putting the pieces together:

class LoRALinear(nn.Module):
    def __init__(
        self,
        base_layer: nn.Linear,
        r: int = 8,
        alpha: float = 16.0,
        dropout: float = 0.0,
    ):
        super().__init__()

        if r <= 0:
            raise ValueError("LoRA rank must be positive")

        self.in_features = base_layer.in_features
        self.out_features = base_layer.out_features
        self.r = r
        self.alpha = alpha
        self.scaling = alpha / r
        self.merged = False

        # Reuse the pretrained parameters.
        self.weight = base_layer.weight
        self.bias = base_layer.bias

        # Freeze the pretrained path.
        self.weight.requires_grad_(False)
        if self.bias is not None:
            self.bias.requires_grad_(False)

        # Match the pretrained layer's placement and precision.
        factory_kwargs = {
            "device": self.weight.device,
            "dtype": self.weight.dtype,
        }

        # A: r x d_in
        self.lora_A = nn.Parameter(
            torch.empty(r, self.in_features, **factory_kwargs)
        )

        # B: d_out x r
        self.lora_B = nn.Parameter(
            torch.empty(self.out_features, r, **factory_kwargs)
        )

        self.dropout = (
            nn.Dropout(dropout)
            if dropout > 0.0
            else nn.Identity()
        )

        self.reset_parameters()

    def reset_parameters(self):
        nn.init.kaiming_uniform_(self.lora_A, a=5**0.5)
        nn.init.zeros_(self.lora_B)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        if self.merged:
            return F.linear(x, self.weight, self.bias)

        # W_0 x
        base_output = F.linear(
            x,
            self.weight,
            self.bias,
        )

        # x A^T
        adapter_output = F.linear(
            self.dropout(x),
            self.lora_A,
        )

        # x A^T B^T
        adapter_output = F.linear(
            adapter_output,
            self.lora_B,
        )

        # W_0 x + (alpha / r) B A x
        return base_output + adapter_output * self.scaling

    @torch.no_grad()
    def merge(self):
        if self.merged:
            return

        delta_w = self.lora_B @ self.lora_A
        self.weight.add_(delta_w * self.scaling)
        self.merged = True

    @torch.no_grad()
    def unmerge(self):
        if not self.merged:
            return

        delta_w = self.lora_B @ self.lora_A
        self.weight.sub_(delta_w * self.scaling)
        self.merged = False

Applying LoRA to an existing model

Of course, creating one LoRALinear layer by hand isn't particularly useful. We want to take an existing pretrained model and replace selected linear projections with LoRA-enabled versions.

Suppose a Transformer contains modules named:

layers.0.self_attn.q_proj
layers.0.self_attn.k_proj
layers.0.self_attn.v_proj
layers.0.self_attn.o_proj
layers.1.self_attn.q_proj
...

and we want to adapt only q_proj and v_proj.

We can walk through all modules in the model and filter them by their final component:

def inject_lora(
    model: nn.Module,
    target_modules: list[str],
    r: int = 8,
    alpha: float = 16.0,
    dropout: float = 0.0,
) -> nn.Module:

    replacements = []

    for name, module in model.named_modules():
        module_name = name.split(".")[-1]

        if module_name not in target_modules:
            continue

        if not isinstance(module, nn.Linear):
            continue

        replacements.append((name, module))

Those two continue statements are filters.

If the module name is not one we want, we skip to the next module. Even if its name matches, we also skip it unless it is an nn.Linear.

Only modules satisfying both conditions make it into replacements.

I collect the replacements first rather than modifying the module tree while iterating over it. Once the search is finished, we can replace them safely:

    for name, module in replacements:
        if "." in name:
            parent_name, child_name = name.rsplit(".", 1)
            parent = model.get_submodule(parent_name)
        else:
            parent = model
            child_name = name

        parent._modules[child_name] = LoRALinear(
            base_layer=module,
            r=r,
            alpha=alpha,
            dropout=dropout,
        )

    return model

The full function is therefore:

def inject_lora(
    model: nn.Module,
    target_modules: list[str],
    r: int = 8,
    alpha: float = 16.0,
    dropout: float = 0.0,
) -> nn.Module:
    replacements = []

    # First find the layers we want to replace.
    for name, module in model.named_modules():
        module_name = name.split(".")[-1]

        if module_name not in target_modules:
            continue

        if not isinstance(module, nn.Linear):
            continue

        replacements.append((name, module))

    # Then replace them.
    for name, module in replacements:
        if "." in name:
            parent_name, child_name = name.rsplit(".", 1)
            parent = model.get_submodule(parent_name)
        else:
            parent = model
            child_name = name

        parent._modules[child_name] = LoRALinear(
            base_layer=module,
            r=r,
            alpha=alpha,
            dropout=dropout,
        )

    return model

Freezing everything except LoRA

The LoRALinear class freezes the pretrained weight inside each replaced layer, but the rest of the model may still contain trainable parameters.

For a conventional LoRA setup, we want only the adapter matrices to receive gradients.

def freeze_non_lora(model: nn.Module):
    for name, parameter in model.named_parameters():
        parameter.requires_grad = "lora_" in name

We can also collect only the adapter parameters when constructing the optimiser:

def get_lora_parameters(
    model: nn.Module,
) -> list[nn.Parameter]:
    return [
        parameter
        for name, parameter in model.named_parameters()
        if "lora_" in name
    ]

Now our setup becomes:

model = load_pretrained_llama()

model = inject_lora(
    model,
    target_modules=[
        "q_proj",
        "k_proj",
        "v_proj",
        "o_proj",
    ],
    r=8,
    alpha=16,
)

freeze_non_lora(model)

lora_parameters = get_lora_parameters(model)

optimizer = torch.optim.AdamW(
    lora_parameters,
    lr=1e-4,
)

The optimiser never even sees the billions of frozen parameters. It receives only \(A\) and \(B\) from each adapter.

Where the memory savings actually come from

This distinction is important: LoRA does not make the pretrained model disappear from GPU memory.

We still need its weights to calculate:

$$W_0x.$$

The major savings come from what we no longer need to store for those weights.

With full fine-tuning:

$$W_0 \quad \text{is trainable}$$

so its parameters need gradients and optimiser state.

With LoRA:

$$W_0 \quad \text{is frozen}$$

so gradients and optimiser state are needed only for \(A\) and \(B\).

An example with LLaMA-7B

The original LLaMA-7B has 32 Transformer layers with hidden size 4096. Its attention projections are \(4096\times4096\).

For rank-8 LoRA, one such projection adds:

$$8(4096+4096)=65,536$$

trainable parameters.

If we adapt Q, K, V and O, there are four adapters per Transformer layer:

$$4\times65,536=262,144$$

LoRA parameters per layer.

Across 32 layers:

$$32\times262,144=8,388,608.$$

That's about 8.4 million trainable parameters.

Compared with a roughly 7-billion-parameter model:

$$\frac{8.4\text{M}}{7\text{B}}\approx0.12\%.$$

So in this configuration, only around one tenth of one percent as many model parameters are being optimised.

This is why LoRA's memory reduction can be so dramatic. Instead of allocating Adam state for billions of parameters, we allocate it for millions.

What about activations?

LoRA does not eliminate activation memory.

We still need to perform a forward and backward pass through the network because gradients for later adapters depend on activations produced by earlier layers.

Activation memory therefore remains an important part of the training footprint, especially as batch size and sequence length increase.

Techniques such as gradient checkpointing can be combined with LoRA to reduce this further, at the cost of additional computation.

This is why statements such as "LoRA training requires exactly X GB" should be treated carefully. Peak memory depends on precision, sequence length, batch size, optimiser implementation, checkpointing, attention implementation, framework overhead, and other details.

The robust claim is simpler: LoRA removes the need for gradients and optimiser states for the vast majority of the base model's parameters.

Counting LoRA parameters correctly

For any linear layer with

$$W\in\mathbb{R}^{d_{\text{out}}\times d_{\text{in}}},$$

the LoRA parameter count is:

$$r(d_{\text{in}}+d_{\text{out}}).$$

We can encode that directly:

def lora_parameter_count(
    in_features: int,
    out_features: int,
    r: int,
) -> int:
    return r * (in_features + out_features)

This is better than assuming every target layer is square.

Attention projections are often easy to reason about, but MLP projections are usually rectangular, and in architectures using grouped-query attention the key and value projections may also differ in size from the query projection.

For the original LLaMA-7B, the attention matrices are \(4096\times4096\), while the MLP expands from 4096 to 11008 before projecting back down.

At rank 8:

r = 8
d_model = 4096
d_ff = 11008
n_layers = 32

attention_per_matrix = lora_parameter_count(
    d_model,
    d_model,
    r,
)

mlp_per_matrix = lora_parameter_count(
    d_model,
    d_ff,
    r,
)

attention_total = (
    4
    * n_layers
    * attention_per_matrix
)

mlp_total = (
    3
    * n_layers
    * mlp_per_matrix
)

print(f"Attention only: {attention_total / 1e6:.2f}M")
print(
    "Attention + MLP: "
    f"{(attention_total + mlp_total) / 1e6:.2f}M"
)

This gives approximately:

Attention only: 8.39M
Attention + MLP: 19.99M

Even adapting all of those matrices leaves the number of trainable parameters tiny relative to the full model.

Which layers should we adapt?

LoRA does not require us to adapt every linear transformation in the network.

In the original paper, much of the analysis focused on attention projection matrices, including \(W_q\), \(W_k\), \(W_v\), and \(W_o\), with particular experiments targeting combinations such as query and value projections.

Modern LoRA configurations vary considerably. Common choices include:

  • Query and value projections only
  • All attention projections
  • Attention and MLP projections

There is a trade-off.

Adapting more matrices gives the model more trainable capacity, but increases parameter count and optimiser state. The right choice depends on the model, dataset, task and available memory.

The important thing is that the maths does not change. For every target matrix, we add another pair:

$$A,\;B.$$

Choosing the rank

The rank \(r\) is one of LoRA's most important hyperparameters.

Increasing it does two things:

  1. It increases the number of trainable parameters.
  2. It increases the maximum rank, and therefore the expressive capacity, of \(\Delta W\).

For a layer with dimensions \(d_{\text{in}}\) and \(d_{\text{out}}\), the parameter count grows linearly with rank:

$$N_{\text{LoRA}} = r(d_{\text{in}}+d_{\text{out}}).$$

For our \(4096\times4096\) example:

  • \(r=4\): 32,768 parameters
  • \(r=8\): 65,536 parameters
  • \(r=16\): 131,072 parameters
  • \(r=32\): 262,144 parameters

There is no universal rank that is optimal for every task. Low ranks such as 8 or 16 are reasonable starting points because they keep the adapter extremely small while still providing non-trivial adaptation capacity.

If validation performance suggests that the adapter is too constrained, rank is one knob we can increase.

But rank should not be considered in isolation. Target modules, learning rate, scaling, dataset size and training duration can matter just as much.

A simple training loop

Once LoRA has been injected, the training loop itself is almost disappointingly normal.

The key difference is simply which parameters we give to the optimiser.

def train_with_lora(
    model: nn.Module,
    train_dataloader,
    num_epochs: int = 3,
    lr: float = 1e-4,
    device: str = "cuda",
):
    model = model.to(device)
    model.train()

    lora_params = get_lora_parameters(model)

    optimizer = torch.optim.AdamW(
        lora_params,
        lr=lr,
    )

    print(
        "Trainable LoRA parameters:",
        f"{sum(p.numel() for p in lora_params):,}",
    )

Then the training step looks just like ordinary fine-tuning:

    for epoch in range(num_epochs):
        for batch in train_dataloader:
            input_ids = batch["input_ids"].to(device)
            labels = batch["labels"].to(device)

            outputs = model(input_ids)

            logits = (
                outputs
                if isinstance(outputs, torch.Tensor)
                else outputs.logits
            )

            loss = F.cross_entropy(
                logits[:, :-1, :].reshape(
                    -1,
                    logits.size(-1),
                ),
                labels[:, 1:].reshape(-1),
                ignore_index=-100,
            )

            optimizer.zero_grad()
            loss.backward()

            torch.nn.utils.clip_grad_norm_(
                lora_params,
                max_norm=1.0,
            )

            optimizer.step()

    return model

The loss still backpropagates through the entire computation graph.

But when it reaches a frozen pretrained parameter, PyTorch does not need to accumulate a gradient for that parameter. When it reaches \(A\) or \(B\), it does.

That is the practical meaning of parameter-efficient fine-tuning.

Saving only the adapter

Another advantage of keeping the adaptation separate from the pretrained model is that we do not need to save a second copy of the entire base model.

We can save only parameters whose names contain lora_:

def save_lora_weights(
    model: nn.Module,
    path: str,
):
    lora_state_dict = {
        name: tensor.cpu()
        for name, tensor in model.state_dict().items()
        if "lora_" in name
    }

    torch.save(
        lora_state_dict,
        path,
    )

And restore them later:

def load_lora_weights(
    model: nn.Module,
    path: str,
):
    lora_state_dict = torch.load(
        path,
        map_location="cpu",
    )

    model.load_state_dict(
        lora_state_dict,
        strict=False,
    )

    return model

This is one reason LoRA adapters are convenient to distribute. The adapter can be orders of magnitude smaller than the model it modifies.

Of course, the recipient still needs the corresponding base model. A LoRA adapter is not a standalone model checkpoint.

Merging for deployment

If we want the simplest possible inference path, we can merge all adapters into their corresponding base matrices:

def merge_lora_weights(model: nn.Module):
    for module in model.modules():
        if isinstance(module, LoRALinear):
            module.merge()


def unmerge_lora_weights(model: nn.Module):
    for module in model.modules():
        if isinstance(module, LoRALinear):
            module.unmerge()

Before merging, each adapted layer computes:

$$W_0x+\frac{\alpha}{r}BAx.$$

After merging, it computes:

$$ \left( W_0+\frac{\alpha}{r}BA \right)x. $$

These are mathematically equivalent.

That is one of LoRA's elegant properties: the extra trainable branch used during fine-tuning can disappear entirely from the deployed computation graph.

Testing the implementation

There are a few properties I want to test rather than simply trusting the implementation.

First, inserting LoRA should not change the model's output before training because \(B=0\).

Second, only LoRA parameters should remain trainable.

Third, gradients should reach the adapters.

Let's make a small Transformer-like model:

class SimpleModel(nn.Module):
    def __init__(
        self,
        d_model: int = 512,
        n_layers: int = 4,
        vocab_size: int = 1000,
    ):
        super().__init__()

        self.d_model = d_model

        self.embed = nn.Embedding(
            vocab_size,
            d_model,
        )

        self.layers = nn.ModuleList([
            nn.ModuleDict({
                "q_proj": nn.Linear(
                    d_model,
                    d_model,
                    bias=False,
                ),
                "k_proj": nn.Linear(
                    d_model,
                    d_model,
                    bias=False,
                ),
                "v_proj": nn.Linear(
                    d_model,
                    d_model,
                    bias=False,
                ),
                "o_proj": nn.Linear(
                    d_model,
                    d_model,
                    bias=False,
                ),
            })
            for _ in range(n_layers)
        ])

        self.head = nn.Linear(
            d_model,
            vocab_size,
            bias=False,
        )

    def forward(self, x):
        h = self.embed(x)

        for layer in self.layers:
            q = layer["q_proj"](h)
            k = layer["k_proj"](h)
            v = layer["v_proj"](h)

            scores = (
                q @ k.transpose(-2, -1)
            ) / self.d_model**0.5

            attention = F.softmax(
                scores,
                dim=-1,
            )

            h = h + layer["o_proj"](
                attention @ v
            )

        return self.head(h)

Now we can test the identity-at-initialisation property:

def test_lora_initialisation():
    torch.manual_seed(0)

    model = SimpleModel()
    model.eval()

    x = torch.randint(
        0,
        1000,
        (2, 32),
    )

    with torch.no_grad():
        output_before = model(x).clone()

    inject_lora(
        model,
        target_modules=[
            "q_proj",
            "v_proj",
        ],
        r=8,
        alpha=16,
    )

    freeze_non_lora(model)

    with torch.no_grad():
        output_after = model(x)

    torch.testing.assert_close(
        output_before,
        output_after,
    )

    print("Insertion leaves output unchanged.")

This test is directly checking our equation.

Because

$$B=0,$$

we expect

$$ W_0x+\frac{\alpha}{r}BAx = W_0x. $$

Next we can verify which parameters remain trainable:

def print_trainable_parameters(model):
    total = 0
    trainable = 0

    for parameter in model.parameters():
        total += parameter.numel()

        if parameter.requires_grad:
            trainable += parameter.numel()

    print(f"Total parameters: {total:,}")
    print(f"Trainable parameters: {trainable:,}")
    print(
        "Trainable percentage:",
        f"{100 * trainable / total:.3f}%",
    )

Finally, we can check that backpropagation reaches the LoRA parameters:

model.train()

output = model(x)
loss = output.square().mean()

loss.backward()

for name, parameter in model.named_parameters():
    if "lora_" in name:
        grad_norm = (
            None
            if parameter.grad is None
            else parameter.grad.norm().item()
        )

        print(name, grad_norm)

There is an interesting detail in this output.

On the first backward pass, we should expect gradients for \(B\), while the gradient of \(A\) can be zero because \(B\) itself is still zero.

That is not a bug. It is a consequence of the initialisation we deliberately chose.

Going further: QLoRA

LoRA reduces the memory associated with training the base model's parameters, but those frozen weights still need to be stored somewhere.

QLoRA attacks that remaining cost by storing the frozen base model in low-bit precision while keeping trainable LoRA adapters on top.

As a rough lower-bound intuition, 7 billion values stored at four bits each correspond to:

$$ 7\times10^9\times\frac{4}{8} = 3.5\times10^9 \text{ bytes}. $$

So the raw four-bit parameter storage is around 3.5 GB, although an actual quantized model requires additional metadata, scaling values, buffers and runtime memory.

The conceptual LoRA equation remains:

$$W_0x+\frac{\alpha}{r}BAx.$$

But our implementation above cannot simply be dropped into a QLoRA setup unchanged. Quantized layers are generally represented by specialised modules rather than ordinary floating-point nn.Linear layers, and their computation needs to handle quantization and compute dtypes appropriately.

So QLoRA is a natural extension of this article, but it deserves its own implementation.

Practical choices

Once the basic implementation is correct, most real LoRA work becomes a question of configuration.

Rank. Values such as 8 or 16 are sensible starting points, but there is no universally optimal rank. Validate rather than assuming that a larger adapter will necessarily be better.

Target modules. Query/value-only adapters are smaller; adapting all attention projections or including MLP projections provides more capacity at additional cost.

Learning rate. LoRA's optimal learning rate need not be the same as the learning rate you would use for full fine-tuning. Treat it as a hyperparameter rather than inheriting the full-fine-tuning value blindly.

Scaling. Remember that \(\alpha\) and \(r\) interact through \(\alpha/r\). If you change rank, be conscious of whether you also want to change the adapter's explicit scale.

Dropout. LoRA dropout applies regularisation specifically to the adapter path. Whether it helps depends on the task and amount of training data.

Validation. More trainable parameters are not automatically better. Rank, target modules and training duration should ultimately be selected using validation performance.

What this implementation leaves out

The code here is intentionally a transparent implementation of the core LoRA mechanism rather than a replacement for a mature PEFT library.

A production implementation may also need to handle:

  • Mixed-precision training policies
  • Quantized base layers
  • Distributed and sharded training
  • Adapter naming and multiple simultaneous adapters
  • Bias-training policies
  • Saving configuration metadata alongside adapter weights
  • Tied weights
  • Different adapter implementations for embeddings or convolutions
  • Automatic module targeting

But none of those additions change the central idea we have implemented here.

$$\boxed{ h = W_0x + \frac{\alpha}{r}BAx }$$

The pretrained matrix \(W_0\) stays frozen. \(A\) compresses the adaptation into a small rank-\(r\) space. \(B\) maps it back to the layer's output dimension. Only \(A\) and \(B\) are trained.

Beyond vanilla LoRA

LoRA has since become the starting point for a much larger family of parameter-efficient adaptation methods.

  • QLoRA combines low-rank adaptation with a quantized frozen base model.
  • DoRA separates weight magnitude and direction when adapting the model.
  • LoRA+ explores different learning rates for the two low-rank matrices.
  • AdaLoRA dynamically allocates rank across different parts of the model.
  • Other PEFT approaches, such as prompt tuning, prefix tuning and adapters, attack the same broad problem from different directions.

My MSc dissertation explored the complementary nature of parameter-efficient fine-tuning methods extensively, so this is an area I am particularly interested in returning to in future posts.

But vanilla LoRA is the right place to start because the mechanism is remarkably simple once the notation is stripped away.

Final thoughts

LoRA is one of those ideas that becomes more impressive the more closely you look at it.

Full fine-tuning says: if a pretrained matrix has millions of parameters, give all of them freedom to change.

LoRA asks a more interesting question: what if the useful change occupies a much smaller space than the matrix itself?

That one assumption turns

$$\Delta W \in \mathbb{R}^{d_{\text{out}}\times d_{\text{in}}}$$

into

$$\Delta W = BA,$$

where we train only

$$r(d_{\text{in}}+d_{\text{out}})$$

parameters instead of

$$d_{\text{in}}d_{\text{out}}.$$

And the implementation follows almost mechanically from there:

base_output = F.linear(
    x,
    self.weight,
    self.bias,
)

adapter = F.linear(
    self.dropout(x),
    self.lora_A,
)

adapter = F.linear(
    adapter,
    self.lora_B,
)

output = (
    base_output
    + adapter * self.scaling
)

That small block of code contains the entire idea.

The pretrained model provides the knowledge it already has. The low-rank branch learns the change we need. And because that change is represented by a tiny fraction of the original parameter count, fine-tuning becomes dramatically more practical.

Once you understand how the dimensions, initialisation and scaling fit together, LoRA stops feeling like a specialised LLM trick. It becomes what it really is: a very simple constraint on how we allow a pretrained weight matrix to change.
