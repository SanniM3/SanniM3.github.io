KV-Cached Decoding From Scratch

From Multi-Head Attention to Cached Autoregressive Decoding

35 min read

I recently read Sebastian Raschka's article on understanding and implementing KV cache in LLMs. It made for a very good resource for understanding the idea, and I decided to implement the same idea in a GPT-2 implementation, and provide additional breakdowns that helped me fully understand it. This post is essentially me penning down my understanding, with an arguably excessive emphasis on dimensions, until every tensor operation made sense to me.

Suppose an LLM is prompted with:

The cat sat on

We pass the entire sequence through the model and predict the next token. A short refresher on how attention works in the model: we compute the key, value and query vectors for each of the tokens in the sequence, then compute the attention score (i.e. how relevant is the key vector to the query), normalize scores to a probability distribution (attention weights), and use these weights to compute a weighted sum of value vectors in order to get the context vectors (i.e. a representation that holds the combined information gathered from all relevant value vectors).

$$\text{Attention}(Q, K, V) = \text{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right)V$$

Now, say the model predicts the. So far, nothing unusual. But to predict the token after the, the standard generation implementation passes this new entire text the cat sat on the through the model again. That means recomputing the query, key and value vectors for each of The, cat, sat, and on, even though we computed exactly the same vectors one generation step ago.

Generate another token and we do it again.

And again.

The longer the sequence becomes, the more time we spend recomputing representations for tokens whose representations have not changed. This is the problem the KV cache solves.

But KV caching is easier to understand once the underlying model is completely transparent. So in this article, I'll build a GPT-2-style decoder-only Transformer from scratch in PyTorch, starting with embeddings and multi-head causal self-attention, before modifying the attention mechanism to cache its keys and values during autoregressive generation.

More importantly, I'll keep track of the tensor shapes throughout. Most of the apparent complexity in attention disappears once it is clear which dimension represents tokens, which represents attention heads, and exactly which matrices are being multiplied.

By the end, the difference between standard generation and KV-cached generation should reduce to one fairly simple idea:

Without KV cache:
recompute the past + compute the new token

With KV cache:
remember the past + compute only the new token

The rest is implementation detail.

The model we are building

I'll use approximately the configuration of the 124M-parameter GPT-2 model:

cfg = {
    "vocab_size": 50257,
    "context_length": 1024,
    "emb_dim": 768,
    "n_heads": 12,
    "n_layers": 12,
    "drop_rate": 0.1,
    "qkv_bias": False
}

At a high level, the architecture is:

token IDs
   ↓
token embeddings + positional embeddings
   ↓
12 × Transformer blocks
   ↓
final layer normalization
   ↓
linear vocabulary projection
   ↓
Logits (distribution over the vocabulary)

With each Transformer block containing two large pieces, Multi-Head Causal Self-Attention and Feed-Forward Network, with layer normalization and residual connections around them.

Turning token IDs into representations

From the earlier high-level architecture, we note that the transformer does not receive text directly. The tokenizer first maps text into integer vocabulary IDs.

For example:

"The cat sat on"

        ↓ tokenizer

[token_0, token_1, token_2, token_3]

If the batch contains b samples/sequences and every sample or sequence contains num_tokens tokens, the input tensor generally has shape:

(b, num_tokens)

GPT-2 then uses an embedding table, that essentially works as a lookup table to convert token IDs to their corresponding embedding vectors:

tok_emb = nn.Embedding(cfg["vocab_size"],cfg["emb_dim"])

With an embedding dimension of 768, an input tensor of shape (b, num_tokens) becomes (b, num_tokens, 768), because every integer vocabulary ID has become a 768-dimensional vector.

But there is a problem.

Attention itself has no inherent notion of token order. If we gave the model the same set of tokens in a different order, the token embedding alone would not tell which token appeared first, second and so on. GPT-2 incorporated this positional information using a second learnable embedding table. Instead of mapping a token_id to a vector (like we did in the token embedding layer), this table maps each possible position in the sequence to its own vector of size emb_dim = 768. Since the model can process at most context_length tokens, there are context_length possible positional embeddings.

pos_emb = nn.Embedding(cfg["context_length"],cfg["emb_dim"])

For a four-token sequence, the positions are:

0, 1, 2, 3

and each position is mapped to its own 768-dimensional vector.

Adding the token embeddings and the positional embedding together, we have a new representation that is still of dimension (b, num_tokens, 768):

x = tok_embeds + pos_embeds

We can think of this as giving every token two pieces of information:

token embedding       → what am I?
positional embedding  → where am I?

Both will become important later. In particular, the positional embedding becomes slightly tricky once KV caching means the model no longer receives the entire sequence during every decoding step.

Attention

The attention layer begins with three learned linear projections:

W_query = nn.Linear(d_in, d_out, bias=qkv_bias)
W_key   = nn.Linear(d_in, d_out, bias=qkv_bias)
W_value = nn.Linear(d_in, d_out, bias=qkv_bias)

Given:

x: (b, num_tokens, 768)

we compute:

queries = W_query(x)
keys    = W_key(x)
values  = W_value(x)

which gives:

Q: (b, num_tokens, 768)
K: (b, num_tokens, 768)
V: (b, num_tokens, 768)

The easiest intuition I have for these three representations is:

Query → what information am I looking for?
Key   → what information do I contain?
Value → what information should I contribute if selected?

Attention first compares queries with keys. It then uses those comparisons to decide how strongly to combine the values. Note this distinction as it becomes important when we eventually ask why a KV cache stores keys and values but does not bother caching queries.

This model uses twelve attention heads. Since embedding dimension = 768 and number of heads = 12, each head receives 768/12 = 64 dimensional vectors. We refer to this smaller dimension as the head_dimension. Therefore, we can reshape our (b, num_tokens, emb_dim) dimensional queries, keys and values by "splitting" the last emb_dim into a product of num_heads and head_dim. The resulting dimension would change from (b, num_tokens, 768) to (b, num_tokens, 12, 64).

queries = queries.view(b, num_tokens, num_heads, head_dim)
keys = keys.view(b, num_tokens, num_heads, head_dim)
values = values.view(b, num_tokens, num_heads, head_dim)

Note that we have not thrown information away. We have simply interpreted the 768 features as twelve groups of 64 features.

For the attention calculation, it is more convenient to place the head dimension before the token dimension. Here, we are not regrouping the tensor elements, rather, we are swapping the token and head axes so the tensor changes from (b, num_tokens, num_heads, head_dim) to (b, num_heads, num_tokens, head_dim).

queries = queries.transpose(1, 2)
keys    = keys.transpose(1, 2)
values  = values.transpose(1, 2)

Now that we have the queries, keys and values matrices computed, we can compute the attention scores. Like we said earlier, attention scores show how relevant the keys are to a query. And this relevance is computed with a query-key comparison represented as a dot product between the two. Think of similarity measurement with a dot product.

scores = queries @ keys.transpose(2, 3)

Before the multiplication, queries and keys are (b, num_heads, num_tokens, head_dim)-dimensional matrices. For each attention head, we want to compute the dot product between every query and every key. To make the inner dimensions compatible for matrix multiplication, we transpose the last two dimension of the keys from (b, num_heads, num_tokens, head_dim) to (b, num_heads, head_dim, num_tokens). The resulting attention score tensor therefore has shape (b, num_heads, num_tokens, num_tokens).

Sidenote: matrix multiplication is just multiple dot products

It may be useful to pause here and see why this matrix multiplication gives us the attention scores.

Suppose we have three query vectors and three key vectors, with each vector containing two features:

$$Q = \begin{bmatrix} q_{11} & q_{12} \\ q_{21} & q_{22} \\ q_{31} & q_{32} \end{bmatrix}$$

and:

$$K = \begin{bmatrix} k_{11} & k_{12} \\ k_{21} & k_{22} \\ k_{31} & k_{32} \end{bmatrix}$$

Each row of \(Q\) is one query vector, and each row of \(K\) is one key vector.

Since we want to compare every query against every key, we transpose \(K\):

$$K^\top = \begin{bmatrix} k_{11} & k_{21} & k_{31} \\ k_{12} & k_{22} & k_{32} \end{bmatrix}$$

Now we can multiply:

$$QK^\top = \begin{bmatrix} q_{11} & q_{12} \\ q_{21} & q_{22} \\ q_{31} & q_{32} \end{bmatrix} \begin{bmatrix} k_{11} & k_{21} & k_{31} \\ k_{12} & k_{22} & k_{32} \end{bmatrix}$$

Expanding the multiplication gives:

$$\begin{bmatrix} q_{11}k_{11}+q_{12}k_{12} & q_{11}k_{21}+q_{12}k_{22} & q_{11}k_{31}+q_{12}k_{32} \\ q_{21}k_{11}+q_{22}k_{12} & q_{21}k_{21}+q_{22}k_{22} & q_{21}k_{31}+q_{22}k_{32} \\ q_{31}k_{11}+q_{32}k_{12} & q_{31}k_{21}+q_{32}k_{22} & q_{31}k_{31}+q_{32}k_{32} \end{bmatrix}$$

But each entry here is simply a dot product. For example:

$$q_2 \cdot k_1 = q_{21}k_{11} + q_{22}k_{12}$$

So we can think of the resulting matrix as:

$$QK^\top = \begin{bmatrix} q_1 \cdot k_1 & q_1 \cdot k_2 & q_1 \cdot k_3 \\ q_2 \cdot k_1 & q_2 \cdot k_2 & q_2 \cdot k_3 \\ q_3 \cdot k_1 & q_3 \cdot k_2 & q_3 \cdot k_3 \end{bmatrix}$$

Matrix multiplication is essentially allowing us to compute all query-key dot products at once, rather than looping through every query and key pair individually.

You can think of this comparison as shown below. For one head and four tokens, this is essentially:

        K0   K1   K2   K3
Q0      •    •    •    •
Q1      •    •    •    •
Q2      •    •    •    •
Q3      •    •    •    •

Every row belongs to a query. Every column belongs to a key. And every cell is one query-key dot product. This is also where the characteristic cost of attention comes from: for num_tokens tokens, we create roughly num_tokens × num_tokens query-key comparisons.

However, we would ideally not want our model to have access to future tokens when computing the representation of the current token, since during generation, those future tokens have not been generated yet. Hence the need for something we refer to as causal attention.

Making attention causal

GPT's generation is autoregressive. This means it generates one token at a time, then uses the generated token as part of the context for generating the next token. Therefore, when computing the context vector for token at position 2, the model should not be able to obtain information from positions 3, 4, 5 and so on. Otherwise training becomes rather pointless: the model could simply look into the future.

To prevent this, we create a causal mask that we would later use to "cover" the portions of the attention score matrix corresponding to future tokens. Since this mask needs to be able to move to the same device as the rest of the model, we register it as a buffer. That is PyTorch's way of registering a tensor that belongs to the module but is not a learnable parameter.

The mask is initialized with shape (context_length, context_length), which is the largest attention score matrix the model can produce since context_length is the maximum sequence length the model supports. The 1s mark query-key comparisons that should NOT be considered, while the 0s mark valid comparisons.

register_buffer(
    "mask",
    torch.triu(
        torch.ones(context_length, context_length),
        diagonal=1
    )
)

For five tokens:

        K0 K1 K2 K3 K4

Q0      0  1  1  1  1
Q1      0  0  1  1  1
Q2      0  0  0  1  1
Q3      0  0  0  0  1
Q4      0  0  0  0  0

The zeros are the comparisons we consider valid. The ones represent future positions. For Q2, therefore, the only valid comparisons are:

Q2 ↔ K0
Q2 ↔ K1
Q2 ↔ K2

The future does not exist yet. At least as far as the model is concerned.

During computation, we take a slice of mask that corresponds to the size of our actual query-key comparison, which in the standard case would be of shape (num_tokens, num_tokens). We then replace the attention scores corresponding to future positions (i.e. where the mask entry = 1) with negative infinity because the softmax (which would later apply to get attention weights) of negative infinity is zero, essentially zeroing out regions we do not want to consider at that step. We also scale the values of the attention scores by the square root of the dimension of the keys, head_dim, before applying softmax. 

scores.masked_fill_(mask.bool()[:num_tokens, :num_tokens], -torch.inf)
scaled_scores = scores / (keys.shape[-1] ** 0.5)

This gives us the attention weights, which have the same shape as the attention scores, (b, num_heads, num_tokens, num_tokens). The context vectors, which I explained earlier are weighted sums of the value vectors, can be computed at once with matrix multiplication. The attention weights have dimension (b, num_heads, num_tokens, num_tokens), while the values have shape (b, num_heads, num_tokens, head_dim). Multiplying them gives context vectors of shape (b, num_heads, num_tokens, head_dim).

weights = torch.softmax(scaled_scores, dim=-1)
weights = dropout(weights)
context_vectors = weights @ values

After doing this independently for all heads, we transpose the result and merge (num_heads, head_dim) back to emb_dim:

context_vectors = context_vectors.transpose(1, 2)  # (b, num_tokens, num_heads, head_dim)
context_vectors = context_vectors.contiguous().view(b, num_tokens, -1)

So far this is ordinary multi-head causal self-attention. Now we can get to the "wasteful" part.

Standard autoregressive generation keeps recomputing the past

Imagine our tokenized prompt is:

A B C D

The model processes all four tokens, during which it calculates:

Q_A Q_B Q_C Q_D
K_A K_B K_C K_D
V_A V_B V_C V_D

This stage where the model processes the prompt is commonly referred to as the prefill stage. Assume it then predicts E. Now, to predict the token after E, a standard generation loop now sends:

A B C D E

through the model. The attention layer calculates:

Q_A Q_B Q_C Q_D Q_E
K_A K_B K_C K_D K_E
V_A V_B V_C V_D V_E

But there is nothing new about:

K_A K_B K_C K_D
V_A V_B V_C V_D

We literally calculated them during the previous forward pass. Say this then generates another token, F; the model calculates them again, and so on.

This is where KV caching enters.

The KV cache: remember what cannot change

Previous tokens do not change during autoregressive generation. And because the transformer's weights are fixed during inference, the keys and values already computed for those previous tokens do not change either.

So rather than recomputing them, we store them:

register_buffer("cache_k", None,persistent=False)
register_buffer("cache_v", None, persistent=False)

Similar to the mask we created earlier, register_buffer tells PyTorch that these tensors belong to the module and should, for example, move with it between CPU and GPU whenever the model moves devices. The persistent parameter here just tells PyTorch not to include this tensor in the model's state_dict. We set this to False because the KV cache is a temporary inference state, belonging to the prompt currently being generated for, and not to the learned model itself.

Why K and V, but not Q?

If K and V are worth caching, why isn't Q? The answer becomes obvious if we look at what the next decoding step actually needs.

Suppose the sequence is now:

A B C D E

and E is the newest token.

To calculate the context vector for E, we need:

Q_E

to compare against:

K_A K_B K_C K_D K_E

So the score computation is:

Q_E @ [K_A K_B K_C K_D K_E]ᵀ

What would we do with:

Q_A Q_B Q_C Q_D

at this point?

Nothing.

We already calculated the context vectors for those token positions when they were processed (i.e. in the prefill stage). Keys and values are different. Future tokens may still need to attend to every one of them. This stage where we generate additional tokens after the initial one in the prefill stage is referred to as decoding.

So during decoding:

Q → compute only the newest one

K → reuse old ones + compute newest one

V → reuse old ones + compute newest one

That is why it is a KV cache rather than a QKV cache.

Prefill and decoding are two different phases

This distinction makes the implementation much easier to reason about.

Suppose the prompt contains four tokens:

A B C D

The first time the model sees this prompt, there is nothing in the cache. We therefore send all four tokens through the model. This is the prefill stage.

The attention layer calculates:

Q_A Q_B Q_C Q_D
K_A K_B K_C K_D
V_A V_B V_C V_D

and because:

cache_k is None  # i.e. empty

we initialize the cache with the computed keys and values:

cache_k = keys
cache_v = values

So after prefill:

cache K:
K_A K_B K_C K_D

cache V:
V_A V_B V_C V_D

Now suppose the model predicts E. This begins the decoding stage. Instead of passing:

A B C D E

back into the model (like we would have done in the standard attention), we pass only E. Therefore:

num_tokens = 1

and we calculate only:

Q_E
K_E
V_E

The new key and value are appended to their respective caches:

cache_k = torch.concat((cache_k, keys), dim=2)
cache_v = torch.concat((cache_v, values), dim=2)
Why dim=2?

Because my cached layout is of dimension (B, num_heads, num_tokens, head_dim) (see key and value dimension just before score computation above) and therefore the token axis is dimension 2.

So:

old cache: (B, num_heads, 4, head_dim) new key: (B, num_heads, 1, head_dim)
} concatenate New cache: (B, num_heads, 5, head_dim)

The attention calculation then uses:

query:
Q_E

keys:
K_A K_B K_C K_D K_E

That is the entire trick!

Where the actual computation is saved

The difference becomes obvious if we write down the score matrices. Without caching, at sequence length num_tokens:

Q: (num_tokens, emb_dim)
K: (num_tokens, emb_dim)

QKᵀ → (num_tokens, num_tokens)

We recompute the complete attention matrix:

          Keys
       K0 K1 K2 K3 K4

Q0      ×
Q1      ×  ×
Q2      ×  ×  ×
Q3      ×  ×  ×  ×
Q4      ×  ×  ×  ×  ×

With KV-cached one-token decoding:

Q_new:   (1, emb_dim)
K_cache: (num_tokens, emb_dim)

Q_new K_cacheᵀ → (1, num_tokens)

We calculate only:

          Keys
       K0 K1 K2 K3 K4

Q4      ×  ×  ×  ×  ×

One row. The same reduction happens when producing the context vector. Without the cache:

context_vector = (num_tokens, num_tokens) @ (num_tokens, emb_dim)

With cached decoding:

context_vector = (1, num_tokens) @ (num_tokens, emb_dim)

So, an intuitive way of thinking about the saving is that during decoding we have gone from repeatedly multiplying large matrices for every old query to computing essentially a vector against a matrix for the newest query.

But that is not the only saving.

We also stopped recalculating all of the previous keys and values in the first place. The cache saves both pieces of work.

The causal mask becomes strangely simple during decoding

There is one slightly awkward consequence of sending only the newest token through the model.

Suppose prefill processed:

A B C D

and the next token is position 4.

During decoding:

queries:
Q4

keys:
K0 K1 K2 K3 K4

There is only one query in the current tensor, but it is not query position zero.

If we blindly took:

mask[:1, :5]

we would select:

        K0 K1 K2 K3 K4

Q0      0  1  1  1  1

which is completely wrong. Our current query is Q4. So we can keep track of its absolute starting position:

ptr_current_pos = 0

And during the four-token prefill:

ptr_current_pos = 0
num_queries     = 4

we select mask rows:

0:4

and then move the pointer:

0 → 4

The next forward pass contains Q4, so we select:

4:(4+1), where 1 is the number of tokens in the new query. Note that is usually 1 for one-token-at-a-time decoding.

Then the pointer is moved:

4 → 5

and so on.

Interestingly, during standard one-token-at-a-time decoding, this selected mask row is always all zeros.

For Q4:

        K0 K1 K2 K3 K4

Q4      0  0  0  0  0

Of course it is. Every key currently in the cache belongs either to a previous token or to the current token. There are no future keys in existence yet. This means the causal mask is technically doing no useful filtering during ordinary single-token decoding. I still keep the general logic because it also works if multiple new uncached tokens are processed together.

Positional embeddings have the same problem

There is another place where sending only one token causes trouble.

Without caching, a five-token input naturally gets positions:

0 1 2 3 4

But during cached decoding, token 4 arrives as a tensor of sequence length one.

If we wrote:

torch.arange(seq_len)

we would assign it position:

0

which is wrong. So we instead track the starting positions like we did earlier with the mask:

pos_current = 0

During four-token prefill:

positions:
0 1 2 3

pos_current:
0 → 4

The next token then receives:

position = 4

and advances the pointer:

4 → 5

There are therefore two similar-looking counters in the implementation: ptr_current_pos tracks which causal-mask rows belong to the current queries, while pos_current tracks which positional embeddings belong to the current tokens. They move together during normal generation, but they solve two different problems.

It is important to note that the cache belongs to the current generation. When a the model is prompted anew, all of it must be discarded.

def reset_cache():
    cache_k, cache_v = None, None
    # return query start position back to 0
    ptr_current_pos = 0

Every Transformer layer needs its own cache

One final point that is easy to miss: there is not one KV cache for the entire GPT model.

Each Transformer layer has different learned W_query, W_key and W_value matrices. So token A does not have one universal key vector. It has a different key representation at every layer.

With twelve Transformer blocks, conceptually we therefore store:

Layer 1:  K cache + V cache
Layer 2:  K cache + V cache
Layer 3:  K cache + V cache
...
Layer 12: K cache + V cache

So, when a completely new prompt arrives, we must discard the caches of all layers and reset all position trackers to 0.

def reset_kv_cache():
    for block in trf_block:
        block.mha.reset_cache()

    pos_current = 0

Putting cached generation together

The final generation loop has the two phases we discussed earlier: prefill and decoding. But before we start anything, we must make sure all caches are empty and all position trackers are set to 0.

model.reset_kv_cache()

# PREFILL
out = model(prompt, use_cache=True)
next_token = select_next_token(out)

# DECODING
for _ in range(max_new_tokens - 1):  # minus 1 because we already generated one token in prefill
    out = model(next_token, use_cache=True)
    next_token = select_next_token(out)

Note that we must still separately maintain the complete output sequence, as this is what we eventually want to return and decode into text.

A B C D E F G ...

But the model itself does not need that complete tensor on every decode step. Its next forward pass might receive only:

G

with the caches containing the already encoded key and value representations of the preceding tokens.

K_A ... K_F
V_A ... V_F

So there are really two sequences involved in generation:

Complete generated sequence:
A B C D E F G

Input to next cached forward pass:
G

Confusing those two is probably the easiest way to make a KV-cache implementation go wrong.

The cost of decoding still grows as the KV cache grows

KV caching removes a lot of repeated computations, but it does not make the cost of generating each new token constant.

Suppose we have already processed 1,000 tokens. During the next decoding step, we only compute the query, key, and value vecotrs for the new token. However, the new query still needs to be compared against all 1,001 keys currently in the cache.

Q_new @ K_cacheᵀ

If the cache contains 100 tokens, the new query is compared against roughly 100 keys. If it contains 1,000 tokens, it is compared againsts roughly 1,000 keys, and so on. The same applies to computing the context vector, the attention weights for the new query must be applied across all the caches value vectors.

So, as the sequence gets longer, there are more cached keys to compare against and more cached values to combine.

What it removes is the repetitive part: recomputing the attention outputs and K/V projections for all 1,000 old tokens just to generate token 1,001.

In other words:

No KV cache:
reconstruct the history every step.

KV cache:
carry the history forward.

That speed comes at the cost of memory. For every token, every layer needs to retain a key and a value representation. The cache therefore grows with sequence length, batch size and model depth. This is why KV caching solves one inference bottleneck and immediately creates another one: memory.

And that leads naturally to techniques such as Multi-Query Attention, Grouped-Query Attention and PagedAttention, whose job is essentially to make this increasingly enormous cache more manageable.

But before worrying about those optimizations, the important thing is understanding what the cache actually contains. It is not storing tokens. It is not storing attention scores. It is not storing context vectors. It is storing the keys and values that future queries will need again.

KV caching is simply autoregressive attention remembering its past. See here for the entire code
